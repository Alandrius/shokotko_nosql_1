# Аналітична платформа для музичного стрімінгового сервісу

Домашнє завдання 1 з курсу NoSQL: документоорієнтована модель даних MongoDB на датасеті
[Spotify Tracks Dataset](https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset) (114 000 треків).

## Налаштування оточення

Потрібні: Python 3.12, `mongosh` 2.x, кластер MongoDB Atlas (M0).
Перевірено на Python 3.12.3 та mongosh 2.14.1.

1. Встановити залежності:

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   npm install -g mongosh
   ```

2. Створити в корені файл `.env` з рядком підключення до Atlas:

   ```
   MONGO_URI=mongodb+srv://user:password@cluster.mongodb.net/
   ```

3. Завантажити датасет з Kaggle і покласти його в корінь як `dataset.csv`.

Файли `.env` та `dataset.csv` не комітяться (див. `.gitignore`).

## Відповіді на теоретичні питання (частина 1)

### Чому аудіохарактеристики лежать в об'єкті `audio_features`, а не плоско?

Це 12 полів, які описують звучання треку, решта полів - це метадані.
Вкладення відображає цей поділ у самому документі.

**Коли вкладення вигідне:**

- **Читання зручніше.** Щоб показати профіль треку, достатньо вказати `audio_features`, не треба перелічувати 12 імен у проєкції, блок можна цілком виключити (`{ audio_features: 0 }`) або залишити.

**Коли створює проблеми:**

- **Довші шляхи в запитах.** Скрізь пишемо `"audio_features.danceability"`, у лапках; у
  `$match`/`$group` легко забути префікс і отримати порожній результат без жодної помилки.
- **Часткове оновлення.** Оновлювати треба точково (`$set: { "audio_features.tempo": 120 }`), а
  `$set: { audio_features: {...} }` перезапише весь об'єкт і затре решту полів.
- **Незручно, коли поля використовуються окремо.** Якби кожен запит чіпав одне-два поля з різних груп, вкладення нічого б не давало, а лише ускладнювало шляхи.

У наших даних вкладення виправдане: усі 12 полів завжди є в кожному документі, оновлюються разом і ніколи не змінюються окремо від треку.

### Чому виконавці зберігаються як масив, а не як рядок?

У CSV виконавці - один рядок із роздільником `;`, наприклад `"Drake;Travis Scott"`. База не знає,
що це список, для неї це просто текст. В масиві кожен виконавець - окреме значення, яке можна
шукати, індексувати і рахувати. Зручніше робити запити про розподіл за кількістю виконавців.

**Які запити стають простішими:**

- **Точний пошук за виконавцем.**
- **Спільні треки кількох виконавців.**
- **Позиція виконавця.**
- **Кількість виконавців.**
- **Агрегації по виконавцях.**

## Запити частини 2

Усі запити лежать у `queries/part2_queries.js`. Нижче - що робить кожен і чому він написаний саме так.

### Завдання 1. Треки для вечірки

Звичайний `find` з трьома умовами одночасно (логічне і): `audio_features.danceability > 0.7`,
`audio_features.energy > 0.7` та `duration_ms` від 180000 до 300000 включно (`$gte` + `$lte`).
Поля `audio_features.*` вказуємо через крапку, бо вони лежать у вкладеному об'єкті.
Результат: **7 311 треків**, у виводі - топ-10 за популярністю. Для перевірки той самий запит
до плоскої колекції `tracks_raw` дає таку саму кількість.

### Завдання 2. Виконавці, у яких усі треки популярні

Пайплайн: `$group` за `track_id` → `$unwind` по `artists` → `$group` за виконавцем (`$sum`, `$min`,
`$avg`) → `$match` (`tracks_count ≥ 3` і `min_popularity ≥ 60`) → `$sort` → `$limit: 20` →
`$project` з `$round` до одного знака.

Спочатку робимо `$group` за `track_id` оскільки у датасеті лише **89 740 унікальних `track_id`** на 113 999
документів, бо той самий трек може бути в кількох жанрах. Без цього кроку виконавець отримав би в результаті
кілька треків з одного. Наприклад, Måneskin мала б 12 записів замість 5. Для дублікатів
береться найвища `popularity`.

Умова не вказує, за чим сортувати "топ-20", тому сортую за середньою популярністю, далі за
кількістю треків, далі за іменем.

Початок результату:

| artist | tracks_count | min_popularity | avg_popularity |
|---|---|---|---|
| Harry Styles | 3 | 89 | 92 |
| Olivia Rodrigo | 5 | 86 | 87.4 |
| IVE | 3 | 79 | 84 |
| Morgan Wallen | 3 | 81 | 83.3 |
| One Direction | 5 | 80 | 83 |

### Завдання 3. Нетипові треки

Пайплайн по кроках:

1. `$group` за `track_genre`: середній темп (`$avg`), стандартне відхилення (`$stdDevPop`) і
   `$push` усіх треків жанру з потрібними полями.
2. `$addFields`: `outlier_threshold = avg_tempo + 2 * std_tempo`.
3. `$addFields`: `$filter` залишає в масиві лише треки з `tempo > outlier_threshold`.
4. `$project`: поля `genre`, `avg_tempo`, `outlier_threshold` (обидва округлені до 1 знака) і
   `outlier_tracks`.
5. `$sort` за жанром.

Порівняння з порогом робиться до округлення, щоб округлення не змінювало склад результату.
Для `acoustic` отримуємо `avg_tempo: 119`, `outlier_threshold: 178.5` що збігається з прикладом з
умови, серед нетипових - "The Legend of Olog-hai, Pt. 1" (темп 182.379). Ручний розрахунок для цього
жанру дав те саме середнє, відхилення і поріг.

Загалом: 114 жанрів, у 112 є нетипові треки, усього **3 506** нетипових треків. Жанри без
нетипових треків залишаються в результаті з порожнім `outlier_tracks`, бо в умові сказано
"для кожного жанру".

### Завдання 4. Треки для фонової роботи

`find` з чотирма умовами: `audio_features.loudness < -10`, `audio_features.speechiness < 0.1`,
`audio_features.instrumentalness > 0.5` та `explicit: false`. Умова на `explicit` працює, бо поле
збережене як справжній булевий тип, а не рядок на кроці 1. Результат: **9 324 треки**,
перевірка через `tracks_raw` дає таку саму кількість.
